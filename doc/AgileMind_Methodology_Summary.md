## Component 1: Intelligent Planning and Task Automation
**Student:** Jayawardhana L S — IT22563200

The methodology for Component 1 centres on a four-stage automation pipeline for Scrum sprint planning ceremonies, implemented in the `AgileMindTools/` Lambda layer and exposed through the `AjileMindApi` FastAPI backend. The first stage addresses backlog prioritisation through a hybrid machine learning approach that combines the Scaled Agile Framework's Weighted Shortest Job First (WSJF) formula with K-Means clustering for MoSCoW categorisation. Backlog item text is encoded into 384-dimensional dense vector representations using the `all-MiniLM-L6-v2` sentence transformer model (Reimers and Gurevych, 2019), capturing the semantic intent of item descriptions, acceptance criteria, and tags. A Principal Component Analysis model is then fitted exclusively on historical sprint embeddings and applied as a fixed transformation to the current backlog, reducing the dimensionality to three principal components that serve as proxies for the three WSJF sub-scores — User Value, Time Criticality, and Risk Reduction. Project-specific WSJF coefficients for priority and severity weights are learned from historical delivery order (`actual_completed_rank`) using Linear Regression, replacing the fixed-weight assumptions of standard WSJF implementations and making the scoring model self-calibrating per project. The three weighted sub-scores are combined into a Cost of Delay, which is divided by story points to produce the final WSJF score. MoSCoW categorisation is performed by K-Means clustering (`k=4`, `n_init=50`) on a feature matrix that amplifies the WSJF score by a factor of 12.0, forcing the four clusters to align with four distinct business-value levels rather than semantic topic groupings — a design validated by a mean silhouette score exceeding 0.50 on the test dataset.

The second stage automates task decomposition using the spaCy `en_core_web_sm` NLP pipeline. A dynamic vocabulary extractor (`get_dynamic_keywords`) processes the project's entire backlog through tokenisation and Part-of-Speech tagging to identify the top 100 project-specific nouns and verbs by frequency, eliminating the need for pre-defined domain keyword lists. Sub-tasks are generated by pairing action verbs (extracted per sentence, normalised to canonical equivalents to prevent duplicate phrases like "Fix" and "Resolve" being treated differently) with noun chunks matching the project vocabulary. Each candidate sub-task is scored on a quality scale combining informativeness (penalising generic verb-noun pairs) and semantic coherence (TF-IDF cosine similarity against the parent story), with items below 0.25 discarded. Duplicate sub-tasks are filtered by computing cosine similarity against all accepted sub-tasks, with a 0.70 threshold eliminating near-synonymous candidates. Story points from the parent item are distributed across sub-tasks proportionally to a complexity score derived from noun phrase word count and Named Entity Recognition detection. The third stage implements developer assignment through an `AITaskAssigner` class that scores every (task, developer) pair on a 170-point rubric across five categories: technology and stack skill match (60 points), project context fit (20 points), historical performance (40 points), TF-IDF cosine similarity between task text and developer profile (20 points), and a Naïve Bayes posterior probability trained on historical `(task_text, assignee)` pairs (20 points). A running workload accumulator steers subsequent assignments away from already-loaded developers, achieving workload balance across the entire task batch in a single pass. The fourth stage generates multi-slide ASCII sprint review presentations by fetching live sprint data from MySQL, building KPI summary and task breakdown slides, and broadcasting each slide as a discrete Redis channel message for real-time WebSocket delivery to stakeholders, while simultaneously inserting a database notification for Project Managers.

## Component 2: Synchronous Daily Scrum Assistant and Meeting Bot
**Student:** Weerapperuma B E — IT22584236

The methodology for Component 2 is structured around four sub-systems that together automate transcript capture, blocker analysis, task status extraction, and attendance monitoring for the Daily Scrum ceremony. The first sub-system, implemented in `app/services/transcript_service.py`, accepts a raw meeting transcript alongside structured metadata and performs three sequential operations: automatic meeting category classification, participant extraction, and meeting attendance update. Category classification applies a hierarchical keyword match on the meeting title — prioritising `standup` and `daily` over `retrospective` over `planning` — a deterministic approach appropriate for enterprise Agile tools where meeting titles follow predictable naming conventions. Participant extraction uses the regular expression `r'^([^:\n]+):'` with the `re.MULTILINE` flag, matching any line in the standard dialogue format (`Speaker Name: utterance`) and collecting unique, sorted speaker names. The extracted participant list is then written back to the corresponding meeting record in the `meetings.attendees` JSON column by joining on `project_id`, `sprint_id`, and `meeting_date`, creating a self-maintaining attendance history derived entirely from meeting content without manual input.

The second sub-system, implemented in `app/services/daily_blocker_service.py`, queries all task updates with `detected_status = 'BLOCKED'` through a multi-table JOIN that applies `COLLATE utf8mb4_unicode_ci` directives and `TRIM()` wrappers to handle character encoding mismatches and accidental whitespace in stored foreign key values. When AI enrichment is requested, each blocker's description is passed to `app/services/llm_service.py`, which uses LangChain's `OllamaLLM` connector to a locally-hosted `llama3.2` model (`temperature=0.7`, `num_predict=500`). The prompt constrains the model to produce exactly 3–4 numbered recovery steps and one recommended senior mentor role in a specific JSON structure. A two-tier recovery strategy parses the response: the primary tier extracts the JSON substring using `response.find('{')` and `response.rfind('}')` followed by `json.loads`; if this fails, a fallback numbered-list parser handles well-formed but non-JSON responses, guaranteeing that usable suggestions are returned even when the model deviates from the requested format. The third sub-system deploys a second, independent language model — Mistral-7B-Instruct via `llama.cpp` — specifically for structured extraction of task status updates from raw transcript text. This model is invoked at `temperature=0.2`, significantly lower than the advisory model, reflecting that extraction tasks require deterministic accuracy rather than creative diversity. A few-shot prompt with Chain-of-Thought instructions guides the model to identify speaker, ticket reference, detected status, and blocker description for each update, returning a typed list of `TaskUpdateExtract` objects. The fourth sub-system, the Team Rhythm Analyzer, requires no machine learning: it uses a SQL `GROUP BY developer_email` aggregation over the `meetings` table with a `JSON_CONTAINS(attendees, JSON_QUOTE(email))` condition to count each developer's standup appearances in the last N days, flagging developers with two or more consecutive absences as likely unreported silent blockers.

## Component 3: Enhanced Retrospective Automation, Documentation and Recurring Bug Detection
**Student:** Kappagoda K M L P K — IT22579140

The methodology for Component 3 addresses two systematic failures in retrospective data utilisation: recurring bugs that are reported verbally across multiple sprints without ever being formalised as tracked work items, and the inability to query historical meeting reports conversationally. The first sub-system, `RecurringBugService` in `app/services/recurring_bug_service.py`, provides a pipeline from raw report content to automatic backlog promotion. Bug detection begins with a 45-keyword pre-filter (`_is_bug_related`) that matches substrings including HTTP status codes, common defect vocabulary, and technical layer names, ensuring only genuine software defects enter the tracking system. Each qualifying text fragment is passed through a five-step normalisation pipeline: lowercasing, punctuation removal via regex, stop-word removal against a 76-word list, minimum word-length filtering (`len(word) > 2`), and alphabetical sorting of the remaining tokens. The sorted normalised string is then hashed with MD5 (`hashlib.md5(normalised.encode()).hexdigest()`) to produce a 32-character canonical identifier. Because the hash is computed from the sorted word set rather than the original word sequence, two different speakers describing the same bug in different word orders — "login authentication fails" and "authentication login fails" — produce identical hashes and are recognised as the same underlying defect. Bug extraction operates across three report types with distinct section schemas: retrospective reports are scanned for `what_didnt_go_well` and `action_points` entries; daily standup reports are scanned for `team_updates[].blockers` and `blockers_summary`; sprint meeting reports are scanned for `issues_and_risks`. Recurring bugs — those whose hash appears in two or more distinct meetings — are surfaced through a `GROUP BY bug_hash HAVING COUNT(*) >= 2` SQL aggregation ordered by mention frequency. When a project manager triggers backlog promotion, `create_backlog_item()` maps mention frequency to priority and severity (`≥4 mentions → critical`, `≥3 → high`, `≥2 → medium`), inserts a pre-formatted backlog item with a complete occurrence timeline, and marks all contributing `recurring_bugs` records as resolved to prevent duplicate promotion.

The second sub-system implements Retrieval-Augmented Generation (RAG) for conversational querying of historical meeting reports, following the Lewis et al. (2020) framework of grounding LLM responses in retrieved document content. The base class `RAGServiceBase` provides two static methods: `chunk_document()` segments report text into 1000-character chunks with 100-character overlap (using forced-advancement logic to prevent infinite loops on degenerate inputs, and filtering chunks shorter than 50 characters), and `find_relevant_chunks()` scores each chunk by counting query word occurrences and returns the top-3 by score. The `OpenAIRAGService` subclass passes the assembled context — a constrained system prompt explicitly prohibiting use of outside knowledge, the top-3 retrieved chunks, and the user's query — to OpenAI GPT-4 at `temperature=0.2`. The system prompt's explicit instruction to acknowledge uncertainty when the answer is not present in the selected report is the primary hallucination-prevention mechanism, prioritising factual accuracy over response fluency in the enterprise meeting context. The third sub-system, the dynamic documentation generator, populates type-specific report schemas (`daily_standup`, `retrospective`, `sprint_meeting`, `brainstorming`) from structured transcript data and produces Markdown reports that are stored with `report_type` and `transcript_id` foreign keys, immediately available for both RAG querying and recurring bug extraction — creating a closed feedback loop between report generation and defect tracking.

## Component 4: AI-Powered Governance Dashboard
**Student:** Ishani S G C — IT22617378

The methodology for Component 4 integrates four analytically distinct services into a unified governance layer for enterprise Agile projects. The cornerstone is the Trust Index Service (`trust_index_service.py`), which synthesises six project health dimensions into a single composite score using a geometric mean with a floor of 1.0, modelled directly on the United Nations Human Development Index methodology (UNDP, 2020). The six components and their formulas are: Team Availability (`availability_ratio × 100`, sourced from leave data); Velocity Consistency (`max(0, 100 − CV)` where CV is the coefficient of variation of closed sprint velocities, computed as population standard deviation divided by mean velocity); Scope Stability (`max(1, 100 − |scope_change_percentage|)`); Historical Accuracy (average sprint completion rate across all closed sprints from the risk service's sprint progress breakdown); Risk Value (`max(1, 100 − risk_percentage)`); and Delay Value (`max(1, 100 − delay_percentage)`). The geometric mean, implemented as `product^(1/n)` after applying a floor of 1.0 to every component, mathematically penalises extreme imbalance — a project with near-perfect velocity consistency but catastrophically low availability will score substantially lower than an arithmetic mean would indicate. A fixed threshold of `RELEASE_THRESHOLD = 80.0` constitutes a deterministic, machine-readable release readiness gate: `is_ready_to_release = (trust_index >= 80.0)`. When not ready, all components scoring below 60 are surfaced as prioritised insights sorted by ascending score, each containing a structured title, observable symptom, and corrective recommendation.

The Delay Calculation Service (`delay_calculation_service.py`) implements a 14-step velocity-based forecasting algorithm. The core formula computes average velocity as total completed story points divided by completed sprints, projects the remaining sprints needed to finish, derives a calendar-day delay, and then adjusts for team availability: `adjusted_delay_days = raw_delay_days / availability_ratio`, where `availability_ratio = 1 − (total_leave_hours / total_planned_hours)` and is clamped to a minimum of 0.1 to prevent division-by-zero. Five analytical enhancements augment the core: confidence interval forecasting derives best-case, most-likely, and worst-case end dates from the last three sprint velocities; velocity trend analysis compares recent average velocity to overall average to classify trajectory as ACCELERATING, DECELERATING, or STABLE; scope change detection computes a scope change ratio against a baseline of planned sprints multiplied by average velocity, flagging projects exceeding a 15% growth threshold; delay attribution decomposes total delay into three causal buckets (LOW_VELOCITY, AVAILABILITY, SCOPE_CHANGE) by computing each factor's contribution in days; and an early warning system applies four rule-based triggers — velocity drop exceeding 20%, availability below 70%, last sprint completion below 70%, and two or more consecutive sprints below 70% completion — generating structured warnings with quantified symptoms and immediate corrective actions.

The Risk Calculation Service (`risk_calculation_service.py`) evaluates nine configurable risk parameters through a weighted aggregation formula: `total_risk = sum(risk_score_i × weight_i) / sum(weight_i)`, with parameters enabled and weighted through the `tbl_risk_parameters_selection` configuration table. Bug and blocker risk scores apply IEEE 1044-aligned priority weighting (`critical×3 + high×2 + medium×1.5 + low×1`) normalised against the maximum possible weighted score if all bugs were critical. Timeline conflict detection performs pairwise date-range overlap analysis per developer, computing conflict risk as `min(overlap_days / 14.0 × 70, 70) + priority_weight` where `priority_weight` is 30 for critical, 20 for high, and 10 for medium priority overlaps. Developer availability risk identifies developers below a 40% utilisation threshold with no uncompleted work as available for additional capacity allocation. A hypothetical impact calculator enables what-if governance queries: it clones the current metric state via `copy.deepcopy`, applies a unit improvement, recalculates the risk score, and returns the reduction delta, allowing managers to quantify the risk benefit of resolving a single critical bug or blocker before committing to the action.

The LLM Advisory Service (`llm_service.py`) uses LangChain's `OllamaLLM` to connect to a locally-deployed `llama3.2` model (`temperature=0.7`, `num_predict=500`, `base_url="http://localhost:11434"`). Seven risk-type-specific prompts each embed actual project metrics from the `metadata` dictionary — total task counts, developer workload breakdowns, bug priority distributions, sprint velocities — ensuring that generated recommendations are numerically grounded rather than generic. For delay-specific advice, the primary causal attribution (`LOW_VELOCITY`, `AVAILABILITY`, or `SCOPE_CHANGE`) is injected into both the context section and the instruction directive, steering the model toward root-cause-targeted recovery strategies. A singleton `llm_service` instance is created at module load and shared across all API handlers. Response parsing handles numbered outputs in both `1.` and `1)` formats, concatenates continuation lines, and strips Markdown formatting, with a two-tier JSON recovery strategy ensuring usable structured output is returned from blocker suggestions even when the model deviates from the requested JSON schema.
